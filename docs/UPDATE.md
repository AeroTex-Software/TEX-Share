# Updating TEX Share

TEX Share stores all persistent state in a single data directory (SQLite database
plus files and keys). Updating the application never touches that directory, so
the safe procedure is always:

1. **Back up first.**
2. Replace the binary/image.
3. Restart and verify.

Schema migrations run automatically on startup and are additive.

---

## 1. Back up before every update

From the admin UI: **Admin → Backups → Create** (leave *encrypt* enabled).

Or copy the data directory while the service is stopped:

```bash
sudo systemctl stop texshare
sudo tar -C /var/lib -czf texshare-$(date +%F).tar.gz texshare
sudo systemctl start texshare
```

> An encrypted automatic backup needs `backup.key` to restore. Keep a copy of
> `secret.key` and `backup.key` somewhere safe and separate. See
> [BACKUP.md](BACKUP.md).

---

## 2. Docker update

```bash
cd TEX-Share
git pull
docker compose build --pull
docker compose up -d
docker compose logs -f texshare
```

Compose replaces the container in place; the `./data` volume is preserved.
Migrations run on first start of the new version.

To pin a specific release, set the image tag instead of building:

```bash
docker compose pull
docker compose up -d
```

### Rolling back (Docker)

```bash
git checkout <previous-tag-or-commit>
docker compose build
docker compose up -d
```

If the new version migrated the database, restore the backup you took in step 1
*before* starting the old version. Migrations are not automatically reversed.

---

## 3. Manual / source update

```bash
cd TEX-Share
sudo systemctl stop texshare

git pull

# Rebuild the frontend and server.
cd web
npm ci
npm run build
cd ..
go build -trimpath -ldflags "-s -w" -o texshare .

sudo systemctl start texshare
sudo systemctl status texshare
```

> Because the frontend is embedded in the binary, you must run `npm run build`
> **before** `go build`, otherwise the new UI will not be included.

---

## 4. Verify the update

```bash
curl -fsS http://127.0.0.1:3535/healthz
curl -fsS http://127.0.0.1:3535/readyz
```

Then confirm in the admin UI:

- **Admin → Monitoring** shows the new version and a healthy status.
- **Admin → Audit → Verify** reports the hash chain intact.
- Sign in and open a share to confirm downloads still work.

---

## 5. Notes

- **Maintenance mode.** For a controlled window, enable
  **Admin → Settings → Maintenance mode** so visitors see a maintenance page
  while you update.
- **Downtime.** Replacing the container or binary is a brief restart. In-flight
  uploads can be resumed by the client; downloads should be retried.
- **Backups are forward-compatible.** A backup taken on an older version can be
  restored into a newer one. Restoring a backup taken on a *newer* version into
  an *older* binary is not supported.
- **Secrets stay put.** `secret.key` and `backup.key` are never regenerated by an
  update. If they are lost, server-side secrets and encrypted backups become
  unrecoverable.
- **Config drift.** New releases may introduce new settings; they are created
  with safe defaults on startup. Review **Admin → Settings** after a major
  update.
